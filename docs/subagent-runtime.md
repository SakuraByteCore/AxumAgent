# One-shot subagent runtimes

## Contract

`dispatch_agent` is the only model-callable dispatch entry. New tasks have independent contexts: the parent packages the full goal, relevant context, owned files, non-goals, interfaces and acceptance checks. The parent automatically selects worthwhile independent lanes, keeps shared files under one owner, works on the critical path and integrates results. This is model policy, not a deterministic scheduler.

`manage_agent` offers only status/wait/interrupt/close. It cannot send, resume or rebase. A wait expiry is observation, not task failure/cancellation. New requirements become explicit incremental dispatches after checking existing effects; there is no automatic side-effect retry. /agent resume now explains that limitation instead of redispatching failures. Historical session files are not migrated, deleted or replayed. Old UI transcript support remains for historical entries; new one-shot results cannot rebase.

Both backends implement Runtime.start → RunHandle with asynchronous result, wait, cancel and dispose. Default execution has no deadline; an explicit timeout includes startup. OAR startup cannot be immediately interrupted: cancellation waits for a late session and disposes it before completion. Root text only is returned, selecting the last nonempty message when ids exist; native child text/reasoning/tool transcripts are not forged as Pi messages. Cancellation/timeout preserves partial evidence and does not roll back already-applied effects. Abort/dispose are deduplicated. Cleanup failures are separate from execution outcomes and visible in status/results. A failed cleanup retains controlled scope locks/admission occupancy; inspect the owned runtime before restarting work. SDK cancellation is cooperative, so cleanup can await a running tool.

## Backends

- **controlled-pi (default)**: real bundled Pi SDK 0.99.2, independent one-shot session, existing live parent executeTool approval/hooks/provenance bridge. Explicit writeScope and exact testCommands remain enforced. Disjoint scoped edits can run concurrently; tests use a workspace-wide child lock and must wait until editing lanes finish. No default bash, custom tools, recursion or auto-discovered child extensions. Automatic SDK retry and companion recovery prompts are disabled in ephemeral child settings, without writing parent settings. No bridge/legacy command context: read/search ceiling, and writable requests fail explicitly.
- **oar-claude-text (explicit dispatch backend)**: actual vendored @botiverse/oar 0.67.0 Claude native transport/session/kernel and turn observation, not a renamed Pi backend. Node >=24 is checked lazily; ordinary Axum Node >=22.19 operation remains supported. Native installed/authenticated Claude CLI is required, never installed or logged in automatically. Native tools are disabled with --tools ''; strict empty MCP; user/project/local settings sources disabled; hooks disabled, plugins not enabled, skills/chrome/session persistence disabled. Explicit dontAsk, NEVER dangerously-skip-permissions (including patched omitted-mode default). Model cannot pass native launchArgs. Only supplied-text analysis is supported: no filesystem research/write/test; any writeScope/testCommands fails before starting. Ambient provider credentials are scrubbed; native login files remain a trust boundary. CLI flag support is checked locally. This is not an OS sandbox for a malicious executable.

The overall system is **not downgraded to read-only**: normal implementation/tests continue through controlled-pi. OAR native writable parity is deliberately unavailable, not silently widened. Codex is not exposed: OAR defaults danger-full-access and never approval; its public API cannot deny builtins or answer native approvals through the parent bridge. Claude permission modes alone do not enforce path scopes or exact test commands. An MCP bridge without proving native-tool/config bypass closure would not solve this. Dedicated OS isolation / verified native tool replacement is future work.

## Provenance and compatibility

Reference: deepseek-ai/deepseek-harness at f3803c96974ad4a94195fb97e5c637e9c2a3afe3, actual subagent-oar src/run.ts/index.ts and tool-subagent-oar source plus patches/@botiverse__oar@0.67.0.patch. The Cordis/DSH provider itself is not a Pi extension and is not loaded. The vendored dependency-closed Claude subset avoids importing OAR's Pi 1.3 SDK and does not mix it into bundled SDK 0.99.2. Only cross-spawn 7.0.6 and which 2.0.2 are external dependencies, pinned with scripts disabled during lock update. vendor/oar/NOTICE documents modifications and vendor/oar/LICENSE preserves Apache-2.0. pi-agent LICENSE remains MIT; the repository root was already FSL-1.1-ALv2 and is unchanged.

Managed default subagent-policy blocks migrate v1–v4 to v5, preserving surrounding/custom content. Existing custom policies are not wholesale overwritten. Legacy supervisor extension/package/alias loading remains blocked by the existing loader gate; no second delegation tool is introduced.

## Verification boundary (2026-10-28)

Real installed CLI probe: Claude Code 2.1.63 supports the required safety flags, but `claude auth status --json` reports loggedIn=false. Codex reports an existing API-key login; it was not invoked for a task because there is no equivalent safe native backend. No login, key change, CLI installation or billable native model task was performed.

Production acceptance uses the actual Axum pi-agent index → dispatch_agent → Runtime/RunHandle → real bundled SDK with a deterministic offline provider for scoped writes/exact tests, plus actual vendored OAR transport with a reviewed offline Claude stream-json fixture. These prove integration/control flow, not real provider quality or native filesystem enforcement. Native Claude provider completion and native writable OAR remain **unverified/unavailable**, respectively. Runtime structural tests cover startup cancellation, partial evidence, cleanup failures, no duplicate completion/no retry; permission tests cover negative authorization, readonly, symlink/dangling aliases and concurrency. There is no claim that OpenClaw delegation itself tests Axum's subagent feature.
